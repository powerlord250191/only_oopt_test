# Тестовое задание ТОЛЬКООПТ

## 1. Вопросы до начала работы

1. **По каким правилам цену можно публиковать автоматически?** Что считаем сопоставимым предложением по артикулу, бренду, наличию и доставке? Какие ограничения по марже и изменению цены действуют и кто подтверждает исключения?
2. **Какую полноту и свежесть данных считаем достаточной?** Если площадка недоступна, можно ли использовать её прошлый результат, сколько времени он годится и сколько независимых источников нужно по товару?
3. «Каждый час» означает запуск сбора или появление уже обновлённого прайса? Есть ли время, когда его нельзя менять из-за рассылки клиентам?
4. Где сейчас зафиксированы формулы и ручные исключения? Есть ли сохранённые выгрузки и ожидаемые цены, по которым можно сверить обе системы?
5. С каких групп товаров и клиентов начнём пилот, кто разрешает публикацию и как быстро нужно уметь вернуться на прежний расчёт?

Первые два ответа влияют на безопасность выпуска цены. Первый определит, какие предложения попадут в расчёт и какие изменения потребуют подтверждения. Второй определит, продолжать ли расчёт по оставшимся источникам или сохранить текущую цену для конкретного товара.

Для решения предполагаю, что сбор запускается раз в час, товары можно сопоставить по проверенной паре «бренд + артикул», а минимальное покрытие, срок годности данных и пределы изменения цены согласуем до пилота. До согласования автообновление выключено.

## 2. Простая архитектура

1. Планировщик запускает сбор раз в час через существующий фоновый воркер. Для каждого часа создаётся один запуск, а просроченные сборы не накладываются друг на друга.
2. Воркеры запускают парсеры с тайм-аутом на источник и ограничением параллельности, чтобы сбой площадки не задерживал остальные.
3. Результаты и статусы источников сохраняются в PostgreSQL с идентификатором запуска и временем получения. Уникальный ключ запуска, источника и предложения позволяет повторять запись без дублей.
4. Перед расчётом предложения проверяются на сопоставимость, свежесть и корректность, а покрытие источниками оценивается по каждому товару.
5. При сбое одной площадки расчёт по товару продолжается, если оставшихся пригодных данных достаточно по согласованным правилам. Иначе текущая цена сохраняется с указанием причины.
6. Действующие правила наценок, минимальной маржи и ручных исключений сверяются со старой системой, а результаты расчёта с причинами изменения сохраняются как черновик прайса.
7. Система прайсов получает черновик из PostgreSQL через согласованный интерфейс вместо Excel и публикует одобренную версию одной транзакцией. Повторная обработка её идентификатора не создаёт новую публикацию.
8. Сначала новая цепочка считает прайсы параллельно действующей на одинаковых входных данных, без публикации и рассылки. Расхождения разбираем с менеджером и прежним разработчиком.
9. После сверки включаем выпуск для небольшой группы товаров или клиентов через флаг. При проблеме выключаем новый расчёт, возвращаем предыдущую проверенную версию и продолжаем выпуск через действующую систему.

## 3. Код и запуск

Требуется Python 3.10 или новее. Из каталога с файлами выполните:

```bash
python3 -m unittest -v
python3 starter.py
```

Тесты проверяют расчёт по подходящему конкуренту с округлением вниз и сохранение текущей цены при частичном ответе источника. Пример из задания возвращает `Decimal("4728.00")` и `APPLY`.
